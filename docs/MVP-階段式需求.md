# Café Startups 單機桌遊 MVP 階段式需求

> 產品模式路線：先完成單機桌遊並確認玩法正確，再開發區域網路模式，最後才開發線上模式。本文目前只定義單機 MVP；區網與線上需求不得提前混入 MVP 驗收。

> 目前進度：Phase 4 規則補強中（單人隨機電腦玩家、三期完整流程、結算畫面、KPI/市場效果與完整單人 HTTP happy path 已完成）。正式 84 張卡牌逐張校對仍未完成。

## 1. 產品定義

### 1.1 目標

把《Café Startups》核心桌遊流程做成可在本機瀏覽器遊玩的單機遊戲，讓 1 位真人玩家即可開始，並由簡易電腦玩家補足其他席位；先驗證「假設 → 實驗 → 學習 → 驗證商業模式」的循環，再擴充區網與線上連線。

### 1.2 MVP 成功標準

- 1 位真人玩家即可在本機建立並開始一局；MVP 不提供第二位真人加入。
- 單機模式由本機伺服器補足電腦玩家至預設席位數；電腦玩家只從合法選項中隨機行動，不進行策略判斷。
- 任一玩家可從建房開始，完成三個時期並看到最終排名。
- 所有現金、成本、貸款、傳牌、顧客、營收與分數由伺服器計算。
- 新玩家只看 UI 與簡短提示，即可完成一局；每一步都能知道「目前階段、要做什麼、誰尚未完成」。
- Domain 規則測試可重複驗證，固定 seed 能重現同一局。

## 2. 產品模式路線

### Stage A：單機桌遊 MVP（目前）

- 只支援 1 位真人玩家在同一台電腦遊玩。
- 由固定 seed 的 Bot 補足其他席位，驗證完整三期流程、卡牌效果、回合同步、KPI、顧客、營收與結算。
- 驗收重點是玩法正確、狀態可重播、錯誤操作可拒絕，以及玩家看得懂提示。

### Stage B：區域網路模式（後續）

- 單機規則與測試穩定後，才開放同一區網內的真人加入與同步。
- 屆時再啟用房間代碼、真人 session、公開／私有狀態與區網傳輸測試。

### Stage C：線上模式（最後）

- 區網模式穩定後，才處理公開部署、身份、斷線重連、持久化、權限、濫用防護與線上監控。

## 3. MVP 範圍與明確簡化

### 包含

- 1 位真人、本機瀏覽器與本機伺服器的單機遊戲；不足 4 位時由 MVP 隨機電腦玩家補足。
- 建立本機遊戲、選擇創辦人／創業店、準備、開始遊戲與本機狀態恢復；加入房間與斷線重連延後至區網／線上階段。
- 3 時期（第 1 期試營運、第 2 期正式營運、第 3 期擴大營運）、9 階段；每期從第 0 回合開始，完成第 1–6 回合的實驗流程。第 0 回合是發牌後尚未完成行動的初始狀態。
- 合夥人卡、創始店卡、經營管理卡、需求卡、顧客標記、現金與貸款的數位化狀態。
- 9 種關鍵指標與結算分數。
- 現金流量表：每回合結束保存快照；每期第 6 回合完成並結算一次，顯示期初現金、營業收入、卡片支出、利息、本金、增貸與期末結餘。
- 遊戲內活動紀錄與規則提示。

### MVP 簡化

- 先使用完整資料結構搭配可審查的 MVP fixture 卡組；正式 84 張卡牌逐張校對可在資料內容階段完成。
- 私下查看需求卡只由伺服器提供給該玩家的 ephemeral view，不做複雜的秘密情報交易。
- 同步操作以「所有真人與電腦玩家完成後進入下一步」實作，不追求真實倒數計時。
- 電腦玩家採伺服器端隨機決策：只過濾當下合法行動後隨機選一項，不考慮策略、勝率、對手或長期規劃；使用遊戲 seed 以便重現。
- 同分時使用固定玩家順序作為最後排序依據，並在 UI 說明這是數位版 tie-breaker。
- 不先實作真人合夥、新手上路、私人借貸、販售情報、競賽規則等變體。
- 卡牌效果目前依 MVP fixture 的 `kind` 與 `marketChange` 套用：marketing/product/value/resource/channel 分別影響對應的簡化指標與市場需求；正式卡牌的個別特殊文字效果仍需逐張依規則書校對。
- 學習階段由伺服器依需求市場產生固定數量的 MVP 顧客，玩家按一次結算即可完成顧客分配、營收與利息；正式市場袋、需求卡與所有顧客標記變化尚未完整還原。

### 不包含

- 帳號、OAuth、好友、公開配對、聊天室、排行榜。
- 商城、付款、廣告、分析追蹤。
- 原生手機 App、策略型 AI 玩家、旁觀者模式。
- 可由玩家任意修改規則的房主設定（除 seed 外）。

## 4. 使用者故事

1. 作為玩家，我可以在本機建立單機遊戲並開始，系統自動補足 MVP 隨機電腦玩家。
2. 作為玩家，我可以看到自己與電腦玩家的席位、準備狀態與行動進度；MVP 不提供真人加入房間。
3. 作為玩家，我可以查看自己的手牌、現金、牌組、貸款與目前目標。
4. 作為玩家，第 1 期（試營運）結束後可以選擇 2 個關鍵指標；第 2 期結束後可以重選 1 次，之後在實驗回合選牌、傳牌、打出或棄掉牌。
5. 作為玩家，我可以看到需要我行動、等待其他玩家或系統結算的明確提示。
6. 作為玩家，我可以看到顧客需求、排名、顧客數、營收、利息與還款結果。
7. 作為玩家，我可以在每期結算後查看現金流量表，並核對期末現金。
8. 作為玩家，我可以在遊戲結束看到現金得分、兩個關鍵指標得分、總分與排名。
9. 作為開發者，我可以用固定 seed 啟動可重現的測試局。

## 5. 階段式交付

### Phase 0 — 規格與技術骨架

**產出**：`Agent.md`、本文件、Go/React workspace、CI/本機啟動說明。

**需求**：

- 定義 domain state、事件、DTO、錯誤碼與房間生命週期。
- 建立固定 seed、fixture 卡牌與需求卡 JSON schema。
- 建立最小 `/health`、`/api/games` 與前端路由骨架。

**驗收**：Go test、frontend typecheck/build 可通過；可啟動 server/client；文件中的命名與目錄一致。

### Phase 1 — 單機規則引擎

**產出**：不依賴網路的 domain service 與測試。

**需求**：

- 建立遊戲、玩家、初始現金/貸款、合夥人與創始店。
- 在大廳選擇 1 張創辦人卡與 1 張創業店卡；選擇由後端保存，開始遊戲時回傳給本人狀態。
- 實作三時期與假設/實驗/學習狀態機。
- 實作發牌、選牌、依時期傳牌、打牌/棄牌。
- 實作卡片成本：固定金額、缺少圖示每個 20 萬元、金額加圖示。
- 實作貸款上限、利息、還款、非法操作拒絕。
- 實作排名、顧客分配、需求配對、客單價、營收與結算。
- 實作每期一次的現金流量表結算，且結餘公式與後端現金一致。

**驗收**：固定 seed 可自動跑完一局；至少涵蓋牌不在手牌、錯誤階段、資金不足、貸款上限、傳牌方向、同分排序等測試。

### Phase 2 — 房間 API 與同步

**產出**：可由單一玩家開始，也可由多個瀏覽器分頁共同操作的房間後端。

**需求**：

- REST：建立/加入/準備/開始/查詢狀態。
- localhost HTTP/JSON：提供單機狀態與指令；WebSocket 公開／私有狀態推送延後至區網階段。
- 每個 command 帶 `gameVersion`；版本不符時回傳衝突並要求重新同步。
- 斷線重連後恢復同一玩家的 session（MVP 可用匿名 token）。
- 伺服器保存事件紀錄與 seed，供除錯及重播。

**驗收**：單一瀏覽器分頁能由建房完成到遊戲結束；至少 2 個瀏覽器分頁仍能共同遊玩；電腦玩家每次只執行合法行動；重複送出 command 不會重複扣款或加分；非本人不能看到手牌。

### Phase 3 — React 遊戲桌 MVP

**產出**：可操作的完整桌遊 UI。

**需求**：

- 單機開始畫面：創辦人／創業店卡、電腦玩家席位、準備／開始；不顯示真人加入入口。
- 遊戲桌：時期/階段/回合進度、需求區、市佔排名、關鍵指標區、銀行摘要。
- 玩家區：手牌、咖啡館牌組、現金、貸款、顧客、當期營收與操作按鈕。
- 操作流程：選關鍵指標 → 選牌 → 等待真人/電腦玩家完成 → 打出/棄牌 → 顯示系統結算。
- 明確區分公開資訊、自己的私有資訊與尚未揭露資訊。
- 規則提示抽屜、錯誤訊息、重連狀態與行動完成狀態。
- 結算頁顯示總分拆解與重新開局。

**驗收**：新玩家不閱讀原規則書也能依提示，透過單一瀏覽器與隨機電腦玩家走完 happy path；桌面與平板寬度下主要操作不被遮住；刷新頁面可恢復狀態。

### Phase 4 — 規則校對與品質門檻

**產出**：可供內部 playtest 的 MVP release。

**需求**：

- 將 fixture 與規則書逐張比對，補上正式卡牌名稱、分類、成本、圖示、市場變動與最低玩家數。
- 增加 domain property tests 或更多情境測試。
- 增加一條 E2E 測試：4 人完成 3 時期。
- 建立錯誤復原與伺服器重啟策略；MVP 至少能匯出事件紀錄。
- 補齊 README、操作說明、規則差異與已知限制。

**驗收**：規則測試通過、production build 通過、E2E 通過、無高嚴重度資料洩漏或重複結算問題。

### Phase 5 — MVP 後候選項目

- 完整正式卡牌與美術資產校對。
- 遊戲主持人/工作坊模式、真人合夥規則。
- 新手上路、兩人變體、競賽規則、私人借貸與販售情報。
- 帳號與持久化房間、公開配對、聊天室、旁觀者。
- 觀戰回放、遊戲統計、無障礙與多語系。

## 6. 核心狀態與 API 草案

### Game state

```text
Game
  id, status, playerOrder, activePeriod, phase, round
  seed, gameVersion, demandBoard, marketBag, eventLog
Player
  id, displayName, isBot, cash, loans, partner, starterShop
  hand, tableau, selectedKpis, customers, currentPeriodStats, score
```

### Command 草案

```text
POST /api/games                         建立單機遊戲並回傳本機 token
POST /api/games/{id}/setup              選擇創辦人卡與創業店卡
POST /api/games/{id}/start              開始遊戲
GET  /api/games/{id}                    取得目前可見狀態
POST /api/games/{id}/commands           送出遊戲指令
```

`commands` 至少包含：`SET_KPI`、`SELECT_CARD`、`PASS_HAND`、`PLAY_SELECTED_CARD`、`DISCARD_SELECTED_CARD`、`TAKE_LOAN`、`REPAY_LOAN`、`CONFIRM_REVENUE`、`CONFIRM_INTEREST`。

## 7. 驗收情境（最小清單）

1. 1 位真人可在本機建立並開始；系統自動補足電腦玩家，MVP 不接受第二位真人加入。
2. 4 個席位可開始；第 1/3 期順時鐘傳牌，第 2 期逆時鐘傳牌。
3. 每位玩家每期得到 7 張起始手牌；後端在第 0 回合開始實驗，完成第 1–6 回合後剩 1 張覆蓋牌。第 1 期結束後才選 KPI，第 2 期結束後可重選一次。
4. 卡片成本會正確扣款；現金不足可依規則貸款，超過 6 張不得一般增貸。
5. 棄牌會返還 MVP 規定的 20 萬元，且不能再查看或使用該牌。
6. 排名依品牌知名度、產品數、品質數、資源數、現金依序比較。
7. 市場袋隨機顧客、通路顧客、奧客與需求滿足能影響營收。
8. 每期利息正確扣除；第三期結束後能清償/計算貸款與現金得分。
9. 關鍵指標只能各選一個欄位、共兩個，結算分數只計選中的兩項。
10. 重新整理、重連、重送相同 command 不會破壞狀態或洩漏他人手牌。

## 8. 風險與決策待辦

- PDF 文字抽取對圖示與部分卡面資料不完整：正式資料建檔時必須以卡面視覺校對，不可只依抽取文字。
- 實體遊戲含秘密資訊與同步操作：單機 MVP 先驗證本機狀態與 Bot 不會卡住流程；WebSocket 私有訊息與「等待所有人」流程留待區網階段。
- 需求配對涉及同圖示由左至右及卡片可重複用於兩類客群：應以純函式測試固定範例，避免 UI 自行推導。
- 需決定 MVP 是否允許玩家重新開始、遊戲中途離線多久、是否保存未完成遊戲；預設為同一 server 執行期間保存，玩家可在結算後重新開局。
- 需在 playtest 後決定是否加入倒數計時；未確認前不將倒數視為核心規則。
