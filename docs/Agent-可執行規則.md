# Café Startups｜Agent 可執行規則

版本：1.0
用途：提供開發 Agent、規則引擎與測試使用的單一可執行規則基線。
正式來源：根目錄 `Cafe Startups 規則書_2025.pdf`。頁碼以下均指規則書印刷頁碼。

> 這份文件不是給玩家閱讀的簡易說明，而是給 Agent 實作與驗收用的規格。每一條規則都應能轉成狀態、條件、公式或測試案例。

## 0. 規則優先順序

1. 正式規則以 `Cafe Startups 規則書_2025.pdf` 為最高依據。
2. 本文件把正式規則改寫成明確的狀態機、資料欄位與判定順序。
3. 本文件的「MVP 簡化」只適用於數位 MVP；不得反向宣稱為實體遊戲正式規則。
4. 卡牌個別文字、成本、圖示、最低玩家人數與市場變動，必須讀取卡牌資料；不能由卡片顏色或名稱猜測。
5. 規則書圖示若無法由文字抽取還原，標記為 `RULE_REVIEW_REQUIRED`，不可自行補值。
6. 規則不完整時採「拒絕未定義操作」：回傳穩定錯誤，不用猜測值讓遊戲繼續。

## 1. 單位與固定常數

程式內所有金額以「萬元」為單位。顯示給玩家時再加上「萬元」或換算為元。

| 名稱 | 值 | 說明 |
|---|---:|---|
| 初始現金 | 150 | 每位玩家的創業基金 |
| 一般貸款本金 | 50 | 每張貸款卡代表 50 萬元 |
| 每期利息 | 10 | 每張貸款卡在每期學習階段支付 10 萬元 |
| 一般貸款上限 | 6 張 | 同時本金最多 300 萬元 |
| 缺少成本圖示 | 每個 20 | 每缺少一個需求圖示，支付 20 萬元 |
| 棄牌補貼 | 20 | 標準規則棄牌時由銀行支付 20 萬元 |
| 饕客基本客單價 | 10 | 每顆饕客標記的基本營收 |
| 一般客基本客單價 | 10 | 每顆一般客標記的基本營收 |
| 奧客基本客單價 | 0 | 奧客不產生正營收 |

金額不得使用浮點數。任何現金變動都必須由伺服器依規則計算並留下事件紀錄。

## 2. 遊戲資料模型

### 2.1 Game

```text
Game {
  id, seed, gameVersion, localSession
  status: lobby | playing | finished
  period: 1 | 2 | 3（1 = 試營運，2 = 正式營運，3 = 擴大營運）
  phase: hypothesis | experiment | learning | finished
  round: 0..6（0 = 已發牌但尚未完成第一個選牌/傳牌/同步行動）
  playerOrder: [playerId]
  demandBoard: 4 gourmet slots + 4 regular slots
  marketBag: customer tokens
  eventLog: ordered immutable events
}
```
### 2.2 Player

```text
Player {
  id, displayName, isBot, order
  cash, loans
  partner, starterShop
  hand, tableau, discardedCards
  selectedKPIs: exactly 2 distinct KPI ids at game end
  customers, currentRevenue, score
  cashFlow: period statements generated by the server
}
```

### 2.3 現金流量表

每一回合結束都保存一筆回合現金快照；每一期在第 6 回合完成、學習階段結算後再產生一筆期現金流量表。欄位固定為 `beginningCash`、`operatingRevenue`、`otherIncome`、`operatingExpenses`、`interestPaid`、`principalRepayment`、`newLoans`、`endingCash`。期末結餘必須符合：`beginningCash + operatingRevenue + otherIncome - operatingExpenses - interestPaid - principalRepayment + newLoans = endingCash`。前端只能顯示後端資料，不得自行推算或重複結算。

### 2.3 卡片與顧客

卡片至少要有：`id`、`name`、`kind`、`period`、`cost.cash`、`cost.icons`、`icons`、`demand`、`marketChange`、`minPlayers`、`source`。

`kind` 的正式分類：

| kind | 顏色 | 作用與計分對應 |
|---|---|---|
| `resource` | 藍色 | 關鍵資源；成本指標 |
| `product` | 黃色 | 特色產品；產品品項指標 |
| `value` | 紅色 | 價值主張；品質指標 |
| `channel` | 綠色 | 門市通路；提供額外來客 |
| `marketing` | 紫色 | 行銷活動；累加品牌知名度 |
| `partner` | — | 初始合夥人能力 |
| `starter_shop` | — | 初始店面來客能力 |

需求圖示的語意名稱固定為：`coffee` 咖啡、`dessert` 甜點、`beans` 咖啡豆、`taste` 可口美味、`service` 貼心服務、`price` 合理價格。圖示數量是需求卡上每一種圖示的需求數量。

顧客類型固定為：`gourmet` 饕客、`regular` 一般客、`difficult` 奧客。每顆顧客標記在該期結算後必須回收，不得留到下一期。

## 3. 遊戲設置

### 3.1 正式規則

1. 遊戲人數為 2–4 人。
2. 洗勻需求卡，放入 4 張普通需求卡與 4 張進階需求卡；兩列最左側各翻開 1 張，其餘保持秘密。
3. 市場袋初始放入 6 顆一般客與 4 顆饕客。
4. 依玩家人數移除卡片上 `4+` 等不符合人數的經營管理卡，再按時期分成三疊。
5. 每位玩家取得 150 現金、1 張玩家幫助卡、1 個玩家代表物與 2 個關鍵指標標記。
6. 每位玩家選 1 張合夥人卡，面朝上放入自己的咖啡館牌組。
7. 每位玩家隨機抽 3 張創始店卡，選 1 張、支付成本、面朝上放入牌組；不足現金可立即貸款。

### 3.2 數位 MVP 設置

1. 單機 MVP 只允許 1 位真人；開始時由本機伺服器自動補足至 4 個席位，補入的席位標記 `isBot=true`。
2. MVP 不提供第二位真人加入、房間代碼分享、區網同步或線上連線；相關 API 只作為後續階段底座，不列入目前驗收。
3. MVP 使用 `MVPPartnerCards()` 與 `MVPStarterShopCards()` 提供創辦人卡與創業店卡選擇；資料標記 `source: mvp-fixture`，並在 UI 顯示「示意卡片 · MVP」。卡片詳細效果與正式成本仍需逐張校對，不得宣稱已完成正式效果還原。
4. seed 是遊戲隨機性的唯一來源。洗牌、抽牌、抽顧客與 Bot 選擇都必須可由相同 seed 重播。

## 4. 狀態機與合法進入條件

```text
lobby
  -- START_GAME --> period=1, experiment, round=0, deal 7 cards
experiment(round=0..6)
  -- each player selects + plays/discards --> pass remaining hand, round += 1
experiment(round=6 complete)
  -- final card covered --> learning
learning(period=1)
  -- resolve --> period=2, hypothesis, wait for KPI choices
hypothesis(period=2)
  -- all KPI choices complete --> experiment, round=0, deal 7 cards
learning(period=2)
  -- resolve --> period=3, hypothesis, allow one KPI reselection
hypothesis(period=3)
  -- all KPI choices complete --> experiment, round=0, deal 7 cards
  -- learning steps complete, period == 3 --> finished
```

任何 command 都必須先檢查：session、玩家身分、目前 phase、gameVersion、指令是否重複、目標資料是否屬於該玩家。檢查失敗不得部分變更狀態。

推薦錯誤碼：`INVALID_ACTION`、`INVALID_PHASE`、`NOT_YOUR_TURN`、`CARD_NOT_FOUND`、`CARD_ALREADY_SELECTED`、`INSUFFICIENT_CASH`、`LOAN_LIMIT`、`VERSION_CONFLICT`、`RULE_REVIEW_REQUIRED`。

## 5. 假設階段（Hypothesis）

### 正式規則

- 第 1、2 時期：依玩家順序各設定 1 個關鍵指標；一位玩家在一個欄位最多放 1 枚標記，但同一欄位可有多位玩家。
- 第 3 時期：可把自己已有的 1 枚標記移到另一個欄位。
- 進入實驗階段前，玩家必須有 2 枚標記且位置不同。

### 數位 MVP 指令

數位 MVP 的 KPI 時機固定如下：第 1 期（試營運）開始時不選指標；第 1 期結束、進入第 2 期前，每位玩家選 2 個不同指標；第 2 期結束、進入第 3 期前，每位玩家可重選 1 次。所有玩家完成當期選擇後，伺服器才開始下一期。

API 使用 `SET_KPI(kpis=[kpiA,kpiB])`。同一期只能成功設定一次；第 1 期實驗中、已開始下一期後或重複送出，都必須回傳 `INVALID_ACTION`。

允許的 KPI id：

```text
gourmet_satisfaction
regular_satisfaction
total_satisfaction
channel
awareness
products
quality
cost
surplus
```

## 6. 實驗階段（Experiment）

每期開始，將該期牌堆洗牌，依玩家順序每人發 7 張，後端將 `round` 設為 `0`。第 0 回合是「已發牌、尚未完成任何選牌/傳牌/同步行動」的初始狀態；之後完成第 1 至第 6 回合。每回合必須按照下列順序執行，不能由 UI 任意改順序。

### 6.1 選定計畫

每位玩家從自己的手牌選 1 張，建立隱藏的 `selectedCard`。選牌後不可再選第二張，也不可選擇不在自己手牌的卡片。

### 6.2 傳遞手牌

選定卡片不傳遞，其他手牌全部傳遞：

| 時期 | 傳遞方向 |
|---|---|
| 第 1 期 | 順時鐘，傳給左手邊玩家 |
| 第 2 期 | 逆時鐘，傳給右手邊玩家 |
| 第 3 期 | 順時鐘，傳給左手邊玩家 |

所有玩家完成選牌後才可一次性傳遞。伺服器必須以 `playerOrder` 計算目標，不使用前端提供的目標玩家。

### 6.3 同步行動：打出或棄掉

每位玩家對自己的 `selectedCard` 二選一。所有玩家的選擇完成前，不可進入下一回合。

#### A. 打出手牌

1. 計算總成本：

```text
totalCost = cost.cash + 20 * missingCostIcons
missingCostIcons = 成本欄要求的圖示中，玩家牌組尚未持有的數量
```

2. 成本欄空白時，`cost.cash=0` 且 `cost.icons=[]`。
3. 卡片加入牌組前先支付成本；現金不足時可依一般貸款規則增貸。
4. 支付成功後，卡片從手牌移到牌組，套用其卡片功能與 `marketChange`。
5. 卡片有放大鏡功能時，只能在打出當下秘密查看任意 1 張需求卡；事後不可補看，查看後放回原欄位且維持秘密。
6. 任何成本、效果或圖示無法判定時，拒絕打牌並回傳 `RULE_REVIEW_REQUIRED`。

#### B. 棄掉手牌

1. 選定卡片從手牌移到棄牌區/配件庫，面朝下且整局不可再查看或使用。
2. 從銀行取得 20 現金。
3. 棄牌不套用卡片功能、不套用市場變動、不加入牌組。

### 6.4 回合結束

當且僅當每位玩家都已選牌並完成打出或棄牌：

1. 傳遞未選手牌。
2. `round += 1`；因此第 0 回合完成第一輪後變成第 1 回合。
3. 回到 6.1，直到 `round == 6`。
4. 第 6 回合完成後，每位玩家應剩 1 張手牌；將該牌面朝下覆蓋到中央，進入學習階段。

## 7. 學習階段（Learning）

### 7.1 市場變動

翻開本期中央覆蓋卡，逐張套用其 `marketChange`，向市場袋加入指定類型與數量的顧客標記。之後固定再加入 1 顆奧客標記。已翻開的卡片回收，不得再次使用。

數位 MVP 若用簡化顧客產生器取代完整市場袋，必須：

- 標示為 `MVP simplified`；
- 使用 seed；
- 產生結果寫入事件；
- 不把簡化結果當作正式市場袋規則。

### 7.2 翻開需求

翻開當期欄位的 2 張需求卡：上排 1 張饕客需求、下排 1 張一般客需求。只有規則允許的查看者可查看秘密需求卡。

### 7.3 市佔率排名與來客

依下列 tuple 由大到小排序：

```text
(
  brandAwareness,
  productCardCount,
  valueCardCount,
  resourceCardCount,
  currentCash,
  coffeeRecency
)
```

其中 `coffeeRecency` 正式規則是最近喝咖啡者優先；數位版沒有可靠時間資料時，使用固定 `playerOrder` 作為最後 tie-breaker，並在 UI 標示「數位版固定順序平手處理」。

依排名從市場袋抽取顧客，再依自己的門市通路卡與創始店卡取得額外饕客/一般客。官方遊戲板的市場袋抽取數量如下：

| 時期 | 第 1 名 | 第 2 名 | 第 3 名 | 第 4 名 |
|---|---:|---:|---:|---:|
| 第 1 期 | 3 | 2 | 1 | 1 |
| 第 2 期 | 4 | 3 | 2 | 1 |
| 第 3 期 | 5 | 3 | 2 | 1 |

排序必須在抽取前完成；抽取順序使用穩定排名。所有顧客標記都是該玩家本期的暫時資料。

### 7.4 需求配對、平均客單價與營收

對饕客與一般客分別計算。基本客單價都是 10，奧客永遠是 0。

需求卡能否滿足的判定：

1. 只用玩家牌組內特色產品卡與價值主張卡上的需求圖示。
2. 需求卡上的每一種圖示，必須有足夠數量的相同圖示。
3. 同一客群中，相同圖示的需求卡必須由左至右依序配對；不同圖示可不依順序。
4. 一張牌在饕客列最多配對一次，在一般客列也最多配對一次；不可在同一客群重複消耗。
5. 每成功滿足一張需求卡，加入該欄位的客單價增額。

```text
unitPrice[gourmet] = 10 + 已滿足饕客需求欄位增額總和
unitPrice[regular] = 10 + 已滿足一般客需求欄位增額總和
unitPrice[difficult] = 0

revenue =
  unitPrice[gourmet] * gourmetCount
  + unitPrice[regular] * regularCount
  + 0 * difficultCount
```

結算營收後，銀行增加等額現金，`currentRevenue` 設為本期營收，所有顧客標記回收至配件庫。

### 7.5 利息、增貸與還款

1. 每持有 1 張貸款卡支付 10 利息。
2. 現金不足支付利息時，可立即增貸以付息；這種「增貸償息」不受 6 張一般貸款上限限制，且當下不計新增貸款的利息。
3. 利息付清後，可每次支付 50 現金返還 1 張貸款卡。
4. 普通商業行動中的增貸仍受 6 張上限限制。
5. 利息計算、現金扣除與貸款卡變更必須是同一個不可部分提交的 domain transaction。

## 8. 遊戲終止與計分

第三期學習階段完成後進入 `finished`。結算時建議先清償所有貸款：每張貸款卡支付本金 50 加利息 10，共 60。

### 8.1 現金結餘分

```text
cashScore = floor(cashAfterLoanSettlement / 10)
```

若未清償貸款，剩餘每張貸款卡另以 -6 分計算。

### 8.2 關鍵指標分

每位玩家只計算自己選定的 2 個 KPI，不能把 9 項全部相加。

| KPI | 計分 |
|---|---|
| 饕客滿意度 | 4 張饕客需求由左至右成功配對，每張 +5 |
| 一般客滿意度 | 4 張一般客需求成功配對，每張 +4 |
| 全面顧客滿意度 | 8 張需求成功配對，每張 +2 |
| 通路 | 每張門市通路卡 +4 |
| 知名度 | 行銷活動卡知名度點數每 1 點 +1 |
| 產品品項 | 每張特色產品卡 +3 |
| 品質 | 每張價值主張卡 +3 |
| 成本 | 每張關鍵資源卡 +3 |
| 盈餘 | 清償貸款後每 30 現金 +1 |

```text
totalScore = cashScore + score(selectedKPI_1) + score(selectedKPI_2)
```

結算排序：`totalScore` 高者優先；同分比較現金；現金也相同則並列勝利。

## 9. Bot 規則（僅數位 MVP）

Bot 不是策略型 AI。Bot 每次只能從伺服器計算出的合法選項中，以可重現隨機方式選 1 項：

1. 選 KPI：只在第 1 期或第 2 期結束後的 KPI 選擇階段，從合法 KPI 集合隨機選 2 個不同項目；同一期只選一次。
2. 選牌：從自己的當前手牌隨機選 1 張。
3. 行動：在合法的「打出」與「棄掉」中隨機選；若打出因資金/貸款限制失敗，必須改為棄牌。
4. 不讀取或推理對手分數、需求、最佳策略或長期勝率。
5. Bot 行動也必須走同一套 domain legality check，不能由 API 直接改現金、牌組、排名或分數。
6. Bot 每次行動寫入事件，例如 `BOT_SELECTED_CARD`、`BOT_PLAYED_CARD`、`BOT_DISCARDED_CARD`。

## 10. 伺服器與前端邊界

- 伺服器是現金、成本、貸款、牌堆、隨機、需求配對、營收、排名、分數與 phase 的唯一真實來源。
- 前端只送出意圖：`SET_KPI`、`SELECT_CARD`、`PLAY_SELECTED_CARD`、`DISCARD_SELECTED_CARD`、`PASS_HAND`、`TAKE_LOAN`、`REPAY_LOAN`、`RESOLVE_LEARNING`。
- 前端不得送出或要求伺服器信任 `cost`、`revenue`、`score`、`rank`、`customerCount` 或其他計算結果。
- 每個 command 帶 `gameVersion`；版本不一致回傳 `VERSION_CONFLICT` 與最新可見狀態。
- 重複 `commandId` 必須回傳第一次結果，不得重複扣款、加款、加牌或加分。
- 公開狀態不得包含其他玩家手牌、未揭露需求卡或秘密查看內容；自己的手牌只回傳給本人 session。

## 11. MVP 與正式規則差異表

| 項目 | 正式規則 | 目前 MVP 允許的簡化 |
|---|---|---|
| 遊玩模式 | 正式規則為 2–4 人 | 單機 MVP 為 1 真人 + Bot 至 4 席；區網與線上延後 |
| 卡牌資料 | 84 張正式卡牌逐張依卡面 | 可使用 `mvp-fixture`，但要標示來源 |
| KPI 設定 | 第 1 期結束後設定，第 2 期結束後可重選一次 | `SET_KPI` 每期只接受一次，所有玩家完成後才進入下一期 |
| 顧客與市場袋 | 依卡片變動、需求、排名與通路完整計算 | 可由固定 seed 的簡化產生器代替，必須標示 |
| 同步傳輸 | 所有玩家同步完成才前進 | 單機由本機伺服器等待真人與 Bot；區網／線上同步延後 |
| 平手 | 最近喝咖啡者優先 | 使用固定玩家順序 |
| 變體規則 | 真人合夥、私人借貸、競賽等另行啟用 | 預設不啟用 |

如果變更超出此表，先更新本文件與 `docs/MVP-階段式需求.md`，再修改程式；不可只在 UI 或單一 handler 偷渡新規則。

## 12. 最小驗收清單

每次修改規則引擎至少驗證：

1. 固定 seed 產生相同牌序、Bot 行動序列與結果。
2. 1 真人 + 3 Bot 可從建房完成三期並進入結算。
3. 每期每人 7 張起始手牌；後端先處於第 0 回合，完成第 1–6 回合後每人剩 1 張中央覆蓋牌。
4. 第 1/3 期向左傳牌，第 2 期向右傳牌。
5. 成本等於現金欄加上缺少圖示數乘 20；資金不足且無法合法增貸時只能棄牌。
6. 普通貸款不可超過 6 張；利息增貸可處理現金不足情況。
7. 棄牌只得 20，不套用卡片功能或市場變動。
8. 排名依品牌、產品、品質、資源、現金、固定順序判定。
9. 需求配對遵守同圖示左至右與每張牌每客群最多一次。
10. 營收、利息、還款、現金分與兩個 KPI 分數可逐項追溯。
11. 非法 phase、他人手牌、錯誤 gameVersion、重複 command 都被拒絕或冪等處理。
12. 任何 fixture 簡化在 UI、README、事件或測試輸出中都明確標示。
